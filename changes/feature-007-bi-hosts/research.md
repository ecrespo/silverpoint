## 1. What exists to build on

| Piece | Where | What it gives a host |
|---|---|---|
| The render pipeline | `@silverpoint/grounds`: `renderChart(recipe, props, env)`, `toSVGString`, `toChartRootString`, `standaloneSVG`; `styles-text` | A chart as a string, DOM-free, in Node or a browser, deterministic |
| The interaction engine | `@silverpoint/core`: `reduceInteraction(geometry, current, event)`, `stepActive`, `resolveActive` | Pointer and keyboard behaviour as one pure function; an adapter only wires events to it (`packages/react/src/create-chart.tsx`, 151 lines) |
| A JSON description of a chart | `@silverpoint/marp`: `ChartFenceSpec` (`chart`, `data`, `props`, `width`, `height`, `id`, `ground`, `substrate`, `mode`, `palette`) and `parseChartFence`, total and never throwing | The spec a host hands over is already designed, validated and documented (Data Model §2.32) |
| A slug → recipe registry | Twice: `packages/mcp/src/recipes.ts` and `packages/marp/src/fence/recipes.ts` | Rendering "by name" exists, but privately, in two packages |
| A standalone SVG render | `packages/mcp/src/tools/render.ts` (`render_chart`, REQ-543, gate REQ-567) | The "render in Node" of the diagram — private to the MCP package |
| The agent catalog | `packages/mcp/agent-catalog.json`, generated by `tools/agent-catalog` (`generate` / `check`) | Per chart: `data.shape`, `data.fields[] { role, prop, type, required }`, `props[] { name, type, default, doc }`, `demo`, `demoKeys`, `demoSample`; grounds, substrates, palettes |
| React components | `@silverpoint/react`, one subpath per chart | What a React host (Superset, Volto) needs, today |

Sixty charts; their catalog shapes: `categories` 15, `series` 8, `points` 7, `distribution` 7,
`parts` 4, `intervals` 4, `matrix` 3, `links` 3, `single` 3, `hierarchy` 3, `events` 2, `field` 1.
Nearly all read **flat rows through accessor props** (`xKey`, `valueKey`, `sourceKey`…), which is the
shape every BI tool hands over. The exceptions, read from the catalog: `heatmap-chart` (`valuesKey`
is an array per row), `parallel-coordinates-chart` (`dimensions`), `orbit-chart` (`markerKey` is an
array) and the two with no fields at all, `gauge-arc` and `meter-chart` (a value in props).

## 2. What is missing

1. **No framework-free client.** A host that is not React, Vue or Angular (a Power BI visual, a
   Tableau page, a notebook cell, a Django template) has the string but nothing that mounts it,
   measures it, moves the active item with the keyboard or shows the readout.
2. **No single file.** Every consumer today resolves `@silverpoint/*` through a bundler. A notebook
   output, a `.pbiviz`, an n8n node that may carry no runtime dependency and a KNIME view each need
   one self-contained script.
3. **The by-name render is private and duplicated** (§1). A third copy in a new package is the point
   at which two implementations of "spec → picture" start to diverge (Art. 2's rationale).
4. **No description for hosts.** The agent catalog speaks to agents: prop types are TypeScript source
   text (`Accessor<string | number>`, `'all' | 'primary'`). A Power BI `capabilities.json`, a Tableau
   `.trex`, an n8n property list, a KNIME dialog and a Superset `controlPanel` all need the same three
   things in data form: the **roles** a chart binds columns to, the **options** worth a control, and
   the **appearance** enums.
5. **No table → spec function.** Each host would otherwise write its own mapping from "these columns
   in these roles" to props, and its own pivot for the heatmap.
6. **Nothing in Python** outside Reflex.

## 3. Proposal in one paragraph

Add one package here, `@silverpoint/embed`: the chart spec promoted out of the deck fence, a DOM-free
entry (`renderToSVG`, `renderToHTML`), a client (`mount`, a custom element, `mountAll`) that is a
framework-free port of what the three adapters do, and both as a single standalone file. Generate a
**host catalog** next to the agent catalog, and ship `specFromTable` beside it. Everything else is a
satellite repository that either vendors that one file or depends on `@silverpoint/react`.

## 4. The hosts — constraints that shape the design

Facts are cited to the page they were read on (2026-11-20). Where a statement is this document's
inference rather than a documented fact, it is marked *(inference)* and carried as a risk in §7.

### 4.1 Power BI — custom visual (`.pbiviz`)

- A visual is a TypeScript class packaged by `pbiviz`; `capabilities.json` declares `dataRoles`,
  `dataViewMappings`, `objects` (the format pane) and, since API v4.6.0, a required `privileges`
  array, empty when the visual needs none ([capabilities](https://learn.microsoft.com/en-us/power-bi/developer/visuals/capabilities)).
- Certification tests that the visual reaches no external service or resource; the repository must
  carry `eslint-plugin-powerbi-visuals`, and `pbiviz package --certification-audit` flags `fetch`,
  `XMLHttpRequest` and `eval` ([certified visuals](https://learn.microsoft.com/en-us/power-bi/developer/visuals/power-bi-custom-visuals-certified)).
- **Consequences:** the standalone file performs no network call and no dynamic evaluation
  (REQ-644); fonts are inlined or absent (REQ-647); `privileges: []`. One visual with a chart-type
  picker cannot change its `dataRoles` at runtime, so the visual declares a fixed superset of roles
  and maps them per chart — a decision of that repository's design (its spec pack, PBI-DD-02).

### 4.2 Tableau — viz extension (`.trex`)

- A viz extension is a web page plus an XML manifest with a `<worksheet-extension>` element, a
  `<source-location><url>`, and `<encoding>` elements that declare the Marks-card tiles
  ([manifest](https://tableau.github.io/extensions-api/docs/vizext/trex_viz_manifest)).
- Extensions are **network-enabled** (any HTTPS server; `http://localhost` for development) or
  **sandboxed** (hosted by Tableau, no outbound calls). Site administrators allow or block each
  ([Tableau Cloud](https://help.tableau.com/current/online/en-us/dashboard_extensions_server.htm)).
  The same page describes the sandbox host as "legacy" and Exchange hosting as a partner service.
- **Consequences:** the extension is a static site this project hosts (GitHub Pages) and users add
  by `.trex`; an administrator must allow its URL. It makes no call but to its own origin, so it
  could move to a sandboxed host unchanged. An Exchange listing is not a goal of v1.

### 4.3 KNIME — pure-Python node extension

- A Python extension declares nodes with the `knime.extension` API, is bundled with its environment
  (pixi recommended) and is shared as a zipped update site or published on KNIME Community Hub
  ([guide](https://docs.knime.com/latest/pure_python_node_extensions_guide/)).
- A view is an HTML document that "must be self-contained", or an SVG/PNG; static images appear in
  reports while pure-HTML views are skipped unless an image representation is supplied
  ([views API](https://docs.knime.com/ap/latest/python-script-api/views)).
- **Consequences:** the node's view is `renderToHTML`'s self-contained document produced by the
  Python package. A report-ready image needs an SVG, and an SVG needs the engine, which is
  JavaScript: Python cannot produce it without a JS runtime (DD-069). The node offers the HTML view
  always, and the SVG output port only where a runtime is configured.

### 4.4 n8n — community node

- Package name `n8n-nodes-*` (or `@scope/n8n-nodes-*`), keyword `n8n-community-node-package`
  ([submit](https://docs.n8n.io/connect/create-nodes/deploy-your-node/submit-community-nodes)).
- Verified nodes may have **no run-time dependencies**, and since 2026-05-01 must be published from
  GitHub Actions with a provenance statement
  ([guidelines](https://docs.n8n.io/connect/create-nodes/build-your-node/reference/verification-guidelines)).
- **Consequences:** the node cannot depend on `@silverpoint/*` at run time; it bundles the DOM-free
  entry into its own `dist` at build time. Whether a bundled engine satisfies the reviewers, as
  opposed to the automated scanner, is not documented *(inference; risk R4)*.

### 4.5 Apache Superset — viz plugin

- A viz plugin is a React package (`ChartPlugin` with `buildQuery`, `controlPanel`,
  `transformProps`) registered in `MainPreset.js`; the project recommends a fork for highly custom
  types ([how-tos](https://superset.apache.org/docs/contributing/howtos)).
- Superset 6.1 ships an Extensions framework: `.supx` bundles loaded at runtime behind
  `ENABLE_EXTENSIONS`, disabled by default ([overview](https://superset.apache.org/developer-docs/extensions/overview),
  [feature flags](https://superset.apache.org/admin-docs/configuration/feature-flags)).
- **Consequences:** the plugin is a classic npm viz plugin on `@silverpoint/react` first. Whether a
  `.supx` extension can contribute a chart type was not established from the pages read
  *(open; that repository's PoC, SUP-T-02)*.

### 4.6 Databricks and Jupyter

- Notebooks render HTML a library returns (`displayHTML`, `_repr_html_`); no extension is needed.
- AI/BI dashboards' custom visualizations "use the Vega-Lite library to render charts from a JSON
  specification" ([docs](https://docs.databricks.com/aws/en/dashboards/manage/visualizations/custom-visualizations)).
  A silverpoint chart is not expressible as a Vega-Lite specification (hatching, inking, the grounds).
  **Out of scope** (DD-072), as the diagram already says.

### 4.7 Flask, Django

No platform constraint beyond the server's Content-Security-Policy: a template helper must work with
`script-src 'self'` and no inline script, which the custom element with a JSON child gives (REQ-645).

### 4.8 Plone

- Volto (the default frontend, React, MIT) takes add-ons generated with Cookieplone's
  `frontend_addon` template ([Volto 18/19 add-ons](https://6.docs.plone.org/volto/development/add-ons/create-an-add-on-18.html)).
  A block is a React component: `@silverpoint/react` fits as is.
- Classic UI is server-rendered Python. `plone.volto` and the backend are GPLv2; a backend add-on
  that imports Plone is distributed under a GPL-compatible licence, by convention GPL-2.0.

## 5. Where this proposal departs from the diagram

| Diagram | Proposal | Why |
|---|---|---|
| "Render en Node (exists, the MCP uses it)" feeds n8n | n8n bundles `@silverpoint/embed`'s DOM-free entry; the MCP's `render_chart` is re-pointed to the same function | The MCP's function is private and carries the MCP SDK; exporting it from `@silverpoint/mcp` would make an agent package a rendering dependency. One function, two callers, the existing REQ-567 gate proving nothing moved (DD-061) |
| Manifests "generated from the agent catalog" | A **host catalog** is generated here from the agent catalog; each satellite generates its own manifest from the host catalog, and checks it in its CI | The monorepo should not know the schema of `capabilities.json` or `.trex`, nor break when Power BI revises one; the satellites should not parse TypeScript type text (DD-066, DD-068) |
| Flask, Django as two extensions | Sub-packages `silverpoint.contrib.flask` and `silverpoint.contrib.django` of the Python package, no repository of their own | Each is a template helper and a static-file route, version-locked to the file the Python package vendors. Decision D3 |
| Plone Classic UI under the Python package | The same, in its own repository | Different licence (GPL-2.0) and Plone's own packaging |

## 6. Repositories: are new ones needed?

Yes, eight; the argument and the alternatives are in [`repositories/README.md`](repositories/README.md).
In short: a host integration has its own toolchain (`pbiviz`, pixi, the n8n CLI, Cookieplone), its own
registry and review process, its own release cadence driven by the host's versions, and in one case
its own licence. Putting them in this monorepo would tie nine `fixed`-group packages to nine foreign
SDKs. What stays here is what must be identical everywhere.

`reflex-silverpoint-react` needs **no functional change**: it wraps `@silverpoint/react`, which this
feature does not touch. It is affected in one way only: `0.11.0` opens a release line, so by delta-017
it follows with a `0.11.0` of its own and the library pins that export in `0.11.1`.

Names were checked free on 2026-11-20: PyPI `silverpoint`, `collective.silverpoint`,
`django-silverpoint`, `flask-silverpoint`; npm `@silverpoint/embed`, `n8n-nodes-silverpoint`,
`volto-silverpoint`, `superset-plugin-chart-silverpoint`; and the eight repository names under
`github.com/ecrespo`. PyPI `silverpoint` is the one worth reserving first.

## 7. Risks

| ID | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R1 | The standalone file is too large for its hosts (60 recipes ≈ 517 KB of unminified ESM today in `core/dist`; rough.js; three font cuts) | medium | high | PoC 11a measures it before anything depends on it; fonts in a separate `full` file; a per-family split is the fallback (DD-062) |
| R2 | A host's sandbox blocks what the client needs (`ResizeObserver`, constructable stylesheets, inline styles under CSP) | medium | medium | PoC 11a runs under `sandbox="allow-scripts"` and a strict CSP; the client writes styles through the CSSOM only (DD-063) |
| R3 | The framework-free client drifts from the adapters | medium | high | It is held to Art. 3 like an adapter: its DOM is compared to the canonical chart root over the PR matrix (REQ-664) |
| R4 | n8n reviewers reject a bundled engine | medium | low | The node is useful unverified on self-hosted n8n; verification is a goal, not a requirement of the node's v1 |
| R5 | Satellites rot: eight repositories, one maintainer | high | medium | The conformance kit makes "still correct" one CI job; a satellite pins a line and follows it with a mechanical bump; waves (plan §Phase 12) so that no more than three are open at once |
| R6 | Host SDKs move (Power BI API, Tableau API, Superset majors, Volto majors, KNIME AP) | high | medium | Each satellite states the host versions it supports and tests against them; none of that reaches this repository |
| R7 | The Python package is taken for a second engine | low | high | It contains no geometry and no colour (its constitution, PY-Art. 1); every picture comes from the vendored file |
| R8 | KNIME Community Hub's licence and publication requirements were not read in full | — | low | Confirm before `silverpoint-knime`'s first release (its spec pack, open question) |

Each has a recommendation, applied in the drafts that follow. **All twelve approved as recommended (user decision, 2026-11-20, with gate 0).** One addition at the same review: the name `silverpoint` on PyPI is taken by the Python package's first real upload, with no placeholder release (`repositories/silverpoint-python.md`, PY-T-02).
